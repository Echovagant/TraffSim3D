# ADR-013: POI 作为导航终点 —— 任务自带目的地，观测按任务扩展，选优按任务指标

- **Status**: ✅ **Accepted** (2026-11-01)
- **Date**: 2026-11-01
- **Deciders**: Project lead（POI 在产品里的角色）
- **Relates to**: [ADR-011](ADR-011-cooperative-driving-at-an-unsignalised-junction.md)（无信号路口协商）·
  [ADR-012](ADR-012-replacing-the-pivot-with-an-arc.md)（弧线与限速模型）·
  [ADR-008](ADR-008-cross-language-contract-oracles.md)（两层对拍）

## Context

产品侧的 POI 管线（`app/apps/maps/poi.py`，高德 → GCJ-02 → WGS84 → 按路网
自己的原点投影）已经落地：真实地图上能拿到咖啡店、医院、加油站这些**地点**。
问题是——这些地点在**仿真**里还只是图上的一个标记，**没有任务含义**。

Scene 4 v2 的协商任务问的是「谁先过这个路口」，这是个**局部**问题；它的策略
学会了让行，却在「能不能到地方」上没有可测的成绩。真实驾驶里两件事同时发生：
**去某个地方**，并且**路上跟别人协商**。缺了目的地这一半，「学会开车」这个
目标就没有终点。

另一条约束是数据：训练不能用真实 POI。项目自己的深圳福田 OSM 切片
（7.29 MB / **51 715 nodes / 7 320 ways**）里 `amenity` 只有 **10** 个，
`shop / leisure / tourism / office / healthcare / historic` **各 0**，
`public_transport` 196，而 parser **没有 POI 通道**——零 key 的方案既改
parser 又交不出货；供应商的 POI 每次训练都要 key。

## Decision

**训练 env 自带目的地**（`app/apps/rl/poi_navigation_env.py`）：每个驾驶者被
分配一个 POI，要开到那儿，路上照常协商。三个决定：

1. **目的地是合成的，但形状是真的**：POI 摆在路网上、按类别的典型路缘距离
   摆（4.5–5.5 m，靠右那侧）。问题形状（目的地在路口对面、路上有别的车）与
   真实数据相同，坐标是合成的。真实 POI 留在产品侧（§7 的管线）。
2. **观测按任务扩展**：POI 任务的观测是 **33 维** = 29 维基础 + **4 维目的地**
   （ego 帧下的目标偏移 x/z、距离/100、到达标志）。基础那 29 维**与 shipped
   策略完全一致**，所以 POI 任务用**另一套权重**，不覆盖随产品附带的那份。
   维度隔离是硬约束：权重形状不可变，否则前向传播的对拍 fixture 全废。
3. **选优按任务指标，不按累计回报**：训练器现在按「到达数优先、回报次之」
   挑最优 checkpoint。理由是实测：按累计 return 选，选到的是**磨蹭但累计多**
   的策略（best 2287 @ step 15 000，而末步只有 577）——累计回报在这个任务里
   是被污染的指标（谁开得慢谁累积得多）。

**奖励**：

```
reward = -(自己的延误 + 造成的他人延误) - 冲突 - 碰撞
       + 0.2 每米（朝目的地靠近） + 20（到达，到达半径 10 m）
```

量级是量过的：60 m 的车程赚 12、到达再赚 20，而**一次碰撞罚 50** ⇒
撞穿过去从来不划算（`tests/test_rl_poi_navigation.py` 把这条钉住）。

**三条让它可学的设计**（每条都是实测踩出来的）：

1. **POI 必须在路线终点那条臂上**：env 把路线改成 `[进场臂, 出-POI 臂]`。
   否则司机过完路口就开 away from 自己的目的地（实测 3 辆里只有 1 辆到达）。
2. **POI 在路缘、靠驾驶者那侧**：横向差 9.75 m 时车停在离 POI 12–16 m 处
   ——永远到不了（到达半径 10 m）。现在横向差 4.5–5.5 m。
3. **所有 POI 在同一条街**（间隔 10 m）：各走各的臂时根本没有冲突
   （`always_go` 3/3 到达、零冲突）——那不是协商题。改成同一条街后，
   谁先到谁挡着谁（`always_go` 2/3 到达、3.4 次碰撞/窗）。

## Consequences

- **新任务，不是新策略**：随产品附带的那份权重（29 维，网格训出）不变；
  POI 任务是**另一套**权重与另一份观测。两者互不污染。
- **实测（10 seed、3 驾驶者、400 步窗口）**：学到的策略到达 **1.9/3**、
  冲突 **0.4**、碰撞 **2.3**、延误 36.3；`always_go` 到达 2.0/3、冲突 1.0、
  碰撞 3.4、延误 3.1。⇒ **冲突降到 1/2.5、碰撞少 1/3**，代价是**延误高得多**
  （它更保守）。**回报不可直接比**（基线不减速，一路累积更多进度奖励）。
- **诚实的结论**：这一版**没有**训出「又快又安全地送到」的策略。**未解**：
  进度奖励与延误归因再平衡、按到达数做课程（先单目标、再多目标）、
  或把延误归因限制在路口附近而不是全程。
- **浏览器侧的闭环还没做**：选 POI 目的地 → 规划路线 → 第一人称跟随到达，
  需要真实 POI（用户侧的高德 key）才能端到端跑通。训练侧的任务已就位。
- **回归风险**：POI 任务复用了 `drive_core` 的奖励与冲突逻辑，所以 core 的
  任何改动都会影响它的数字——重训与重测要一起做。

## Alternatives considered

- **用真实 POI 训练**：数据量不够（`amenity` 10 个）、要 key、每次训练都要
  网络 ⇒ 拒绝；改成「形状相同、坐标合成」。
- **把目的地编码进路网图（新的节点类型）**：那样 POI 就进了路由，图也会被
  POI 污染（每个 POI 一条 stub）⇒ 拒绝；目的地是**给车的任务**，不是路网。
- **用累计回报选最优 checkpoint**：实测会选到磨蹭策略 ⇒ 拒绝。
- **不给观测加目的地，让策略从路线的终点推**：路线终点与 POI 在不同臂时会
  打架（车该往哪开？），而且要策略去解一个本可以直接给它的量 ⇒ 拒绝。
