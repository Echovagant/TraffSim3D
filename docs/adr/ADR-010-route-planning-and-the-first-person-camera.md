# ADR-010: 路线规划与第一人称跟随 —— 一辆车按计划走，相机坐在它里面

- **Status**: ✅ **Accepted** (2026-10-31)
- **Date**: 2026-10-31
- **Deciders**: Project lead (Scene 3 交付面之后的产品线)
- **Relates to**: [ADR-005](ADR-005-architecture-ddd-split.md)（分层）·
  [ADR-006](ADR-006-map-data-osm-graph.md)（OSM → 内部图）

---

## Context

浏览器里有两样东西一直缺：

1. **没有路线**。后端一直有路由算法 —— `app/apps/maps/road_graph.py` 的节点级
   有向 A\*，训练环境里还有一份段级 Dijkstra（`app/apps/rl/network_graph.py`）——
   但**都没有出口**：没有 HTTP 端点，前端也没有消费者。前端的「轨迹」是行驶
   历史，不是路线。
2. **没有车内视角**。相机只有 `useCameraControls` 的轨道模式（focus / fit 两种
   动画），没有「坐在车里往前看」。

这两件事本来是同一个故事：**规划一条路线，然后坐在车里把它开完**。

同时有一条**不能碰的约束**：浏览器的转向规则是**哈希概率决策**
（`TURN_PROBABILITY = 0.25` / `RIGHT_TURN_SHARE = 0.6`，见
`src/domain/services/roadTransition.ts`），它与 Python 训练环境
（`app/apps/rl/network_signal_env.py`）**同形**。浏览器侧的总延误基线
（**4626.8 veh·s**）与 RL 策略的迁移结论（**−5.0 %**）都是在**这条规则**下
量出来的。⇒ 改全局转向规则会让那些数字失去意义。

## Decision

**路线是一辆车（跟车）的计划；相机可以坐在它里面。其余车辆一切照旧。**

- **后端出端点**：`POST /api/v1/routes/plan`（`app/api/v1/routes.py`）。
  它用**节点级有向图**（`RoadGraph`）—— 单行道只能顺行，且每条 leg 说清
  驶入方向。前端不自己实现 A\*：同一件事只写一遍。
- **起点带方向**。车不在路口上，它在一条路上、正朝这条路的一头去。端点的
  起点因此是「**这条路、这个方向的那一头**」，而不是一个坐标。路径从车
  **下一个到达的节点**开始算 ⇒ 返回的 leg 序列从车所在的位置就是可开的。
  同一路口若两个方向等长，A\* 会挑原路回去 ⇒ 端点禁止**第一条 leg** 就是
  起点那条路（那是在第一个路口掉头）。
- **只有跟车按路线走**。`roadContinuation` 多一个参数：路线指定的下一条路
  **在该路口确实是候选**时采用它；否则**回落到哈希概率规则**（车跑偏了、
  或计划在那个路口不可开）。**其余车辆完全不受影响** ⇒ RL 口径不变。
- **路线画在车实际行驶的车道上**，不是路中线。后端的 leg 是路段级的
  （路口到路口），节点落在中线上，离车 **5.25 m** —— 画在那里读作
  「另一条车道」，恰恰是错误的信息。keep-right 规则让偏移是统一的：
  无论往哪个方向开，车都在**行进方向右侧** `laneOffset(0, laneCount)` 处。
- **第一人称相机接管渲染循环**：相机在跟车时自己定位（眼高
  `DRIVER_EYE_HEIGHT_M = 1.35 m`，前视 14 m、俯视 1.6 m），轨道控件让位；
  跟车**自身不绘制**（相机就在它体内）。
- **不修枢轴碰撞**。路线驱动的转向消除的是「转向与计划矛盾」这一类错误，
  **不改变**转弯车横扫路口角的几何（实测最多 7.4 m）。枢轴仍是模型性质，
  真正的修法是弧线 —— 属于模型改动，不在本轮。

## Consequences

- **产品有了第二条主线**：规划路线 → 开车 → 第一人称跟随。
  随产品附带的网格策略（§5.4）在同一条链路上指挥信号灯。
- **RL 的测量口径不变**：NPC 转向规则一字未动，浏览器的 4626.8 基线与
  −5.0 % 结论仍然有效（这一条由「NPC 转向分布零变化」守住）。
- **路由只有一份实现**：后端。有向、单行道、方向语义都在后端，
  前端只画线、只决定「下一条路」。
- **跟车会离开路线**：计划是建议，路口的实况优先。离开后跟车回到普通规则，
  HUD 的进度条会停在原处 —— 这是诚实的失败，不是 bug。
- **端点不带 torch**：只读 JSON 资产级开销，基础依赖的后端（例如 e2e 的那个）
  也能服务它。
- **视觉基线**：场景编辑器的截图裁剪区（`SCENE_CLIP`）不含路线面板，
  所以既有基线**未动**；第一人称视角是新画面，**新增**基线而不是改旧的。

## Alternatives considered

- **全网每辆车都规划路线**：更「真实」，但请求量大、转向模型大改，
  且会让浏览器与 Python 训练环境的转向规则分叉 ⇒ 拒绝：RL 的测量口径没了。
- **前端自己实现 A\***：离线可用、无往返，但等于把同一模型写两遍 ——
  本仓库最忌讳的漂移源 ⇒ 拒绝。
- **用段级 Dijkstra（`network_graph.find_route`）出端点**：它是训练环境的
  那一套，代价按段长算，且**不带方向**（无法区分驶入方向）⇒ 拒绝：
  产品要的方向语义它没有。
- **在独立的「驾驶舱」页面做第一人称**：更像成品，但要新路由、新渲染入口、
  新的一整套视觉基线 ⇒ 拒绝（本轮）：现有 3D 视图加跟随模式即可，
  工作量与风险都在一个数量级以下。
- **相机放在车顶而不是车内**：省掉「隐藏自身车身」这一步，但视角不再是
  驾驶员视角 ⇒ 拒绝。
