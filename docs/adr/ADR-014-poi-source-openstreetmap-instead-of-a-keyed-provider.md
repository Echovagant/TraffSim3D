# ADR-014: 兴趣点来自 OpenStreetMap —— 不用需要 Key 的商业地图服务

- **Status**: ✅ **Accepted** (2026-11-01)

## Context

产品的 POI 叠加（`POST /maps/poi` → 场景里的彩色标记）原先接的是 **高德
（AMap）** 的 Web 服务 API：高德的数据在国内最全，接口也简单。

但这条路的代价是**要一张 Key**，而 Key 的归属让产品形态变得别扭：

- 高德的免费额度只给**个人认证开发者**（搜索类 5 000 次/月），**商用要另买
  技术服务许可**；百度的商用授权是 **5 万元/年**。产品的运行成本不该绑在一张
  需要申请、需要续期、可能失效的 Key 上。
- Key 要由使用者填写、存在浏览器里（配额归用户）或由部署方配置
  （`TRAFFIC_AMAP_KEY`）——两条路都要用户先做一件与「用仿真」无关的事。
- 高德的数据是 **GCJ-02**（火星坐标），比 WGS84 偏移几百米；POI 落到场景里
  之前必须先做基准反解（那个反演本身还有它自己的近似误差）。

同时有一个被低估的事实：**国内城市的 OSM 覆盖并不薄**。项目自己那份深圳
福田切片里只有 10 个 `amenity`，是因为那份切片是从 `roads.geojson` 生成的
（只留了道路）——**不是 OSM 没数据**。直接查 OSM 数据库（实测，深圳福田一个区）：

| 类目 | 要素数 |
|---|---|
| amenity | 4 516 |
| leisure | 2 193 |
| public_transport | 3 146 |
| shop | 807 |
| tourism | 501 |
| man_made | 1 033 |
| office / healthcare / historic / sport | 217 / 129 / 81 / 1 278 |

名字是中文的（沃尔玛、华润万家、必胜客、味千拉面、7-Eleven、赛格电子市场）。

## Decision

**POI 的来源换成 OpenStreetMap**，通过公共 **Overpass** API 抓取，
**不需要 Key、不需要账号、不产生配额与账单**。

三条支撑规则：

1. **同基准 ⇒ 没有转换步骤**。OSM 是 WGS84，场景的路网也是 WGS84，所以 POI
   只需按**路网自己的投影公式与原点**投影到本地米制，**不做任何基准转换**。
   上一条路径上那套 GCJ-02 反演在这条路径上整体消失——少一个环节，也少一个
   会错几百米的环节。
2. **慢，所以缓存**。Overpass 是志愿者运营的公共服务：实测一个场景尺度的
   矩形要 **50–73 s**，繁忙时还会 502/504（同一个查询在一分钟内先 200、再
   502、再 504）。因此抓取走**实例链**（三个公开实例，共享一个 **100 s 总预算**，
   后面的实例只拿剩余额度，避免不可达的镜像把等待乘三），响应**写磁盘缓存**
   （同一范围第二次加载瞬时），浏览器超时 **120 s**。
3. **查询只取 node，关键词是 AND**。输出配额本来先被 node 填满（实测
   node-only 与 node+way 的查询返回了**完全相同**的 300 个要素），多要 way
   只会更慢。关键词过滤必须挂在**同一个语句**上
   （`node["amenity"]["name"~"咖啡",i]`）——Overpass 的 union 语法是 OR，
   写成独立语句会把查询**放宽**（所有 POI + 名字匹配的 POI）而不是收窄。

类目由 tag 的**取值**决定（`amenity=restaurant` → 餐饮、`amenity=hospital` →
医疗、`shop=*` → 购物），未列出的取值回落到 tag 的类目。约四分之一的 POI
**没有名字**，OSM 在中国的 `addr:*` 门牌数据也少——面板据实显示「(无名)」
与「无地址」。

## Consequences

- **产品侧不需要任何凭据**：面板上的 Key 输入框删掉了，`POST /maps/poi`
  不再接受 `key`，也不再返回 400「没有 Key」。
- **代价是首屏慢**：一次首次加载可能 50–73 s（面板明说「首次加载可能要
  一分钟」，之后走缓存）。这是选「不要 Key」的直接成本。
- **数据质量**：类目与名称够用（实测），但地址基本没有；覆盖面取决于 OSM
  在该城市的丰富度——**这与路网数据是同一份来源的同一个短板**，所以 POI 与
  路网在覆盖上一致（不会出现「有路没店」的错觉，而是「整片区域都少」）。
- **许可**：OSM 数据是 **ODbL**，界面里已有的 OSM 署名必须保留。
- **`coord_transform.py` 仍在**（导入端点仍支持 GCJ-02/BD-09 的**文件**）——
  换掉的是 POI 这条路径，不是坐标转换能力本身。
- **训练侧不变**：RL 任务用的是**合成 POI**（摆在训练路网上），不依赖任何
  外部数据源（见 ADR-013）。
- **未解**：底图（Cesium 的高德瓦片，GCJ-02）与路网（OSM，WGS84）之间**没有**
  做偏移处理 ⇒ Smart City 视图里底图与路网按坐标系推算会错开几百米。这是
  既有状态（不是本决策引入的），要修得另开一轮。

## Alternatives considered

- **继续用高德**：功能更强、数据更全，但把产品的可用性绑在一张要申请、要续期、
  商用还要付费的 Key 上 ⇒ 拒绝（决定性理由）。
- **百度**：同样的 Key 与商用授权问题（5 万/年），且规范文档页抓不到 ⇒ 拒绝。
- **天地图（国家地理信息公共服务平台）**：官方、公益性、**在线服务无偿使用**
  （《地理信息公共服务平台管理办法》第十六条）、全国覆盖——是「要官方数据」
  时的正解；但仍要注册申请 Key，而当前需求是 POI 叠加，不是权威底图 ⇒ 暂不引入。
- **用导入的 OSM 文件里的 POI**：完全离线，但要改 parser 的输出通道，且用户
  导入的文件未必带 POI 节点（项目自己的示例切片就没有）⇒ 以后作为**补充**
  手段，不作为主路径。
- **自己抓一份城市 POI 打包进产品**：一次抓取、永久可用，但要为每个城市维护
  数据量（一个区就 ~14 000 个要素）⇒ 暂不做。
